Plotline becomes Marketing Studio

Owner: Anand · 24 Aug 2026 · Governing brief: docs/SYSTEM-PROMPT-v2-marketing-studio.md. Precedence: v2 > Addendum-02 > Addendum-01 > PRD v1. Sections 01–06 = the new mode. 01 · Where it sits

Two tabs: Campaign Studio, My Campaigns

Marketing Studio is a mode, not a rewrite. The top nav for this mode is Campaign Studio · My Campaigns. A campaign is a series row (series.name = campaign name, series.context = CampaignContext); its threads are the existing threads table with kind='campaign'; the Ad Card reuses the Post Card table shape. No new storage concept enters the product.

  • Campaign Studio — the working surface. Blank landing → campaign name → intake → thread. When the user already has ≥1 campaign, the studio's top bar carries a + New campaign tab/action.
  • My Campaigns — the home of finished and in-flight work (§06). Replaces Plans for this mode.
  • The thread is still the product. Addendum-01's chat-first model is inherited wholesale: agent drives, artifacts render as cards inside agent messages, approvals are dual-path (tap or type), no stage sidebar anywhere.
  • Dark, scoped. The Marketing Studio surfaces run the --ms-* dark token set (§03). Existing light Plotline screens keep working — the dark theme is scoped to this mode's wrapper, the old pages are not globally inverted.
  • What it supersedes: the v1 §12 Content Studio row (already replaced once by Addendum-01) is renamed and re-landed as Campaign Studio; v1's Plans row becomes My Campaigns; Addendum-01's right-panel tab pair changes; Addendum-02's creative director is re-seated as the creative orchestrator. Full map in §08.

StepStates the user sees✚ Fills specified here
0 · Blank landing Near-blank canvas, one block: <Campaign Name> — "Give a name to your campaign." Empty (placeholder) · typing · invalid · submitted. The name is required: it is the My Campaigns handle and the thread numbering root (<Campaign> — 01, Addendum-01 §03 numbering unchanged). ✚ Enter submits. Inline validation: non-empty, unique per workspace. Error renders under the field, the primary stays disabled until it clears.
1 · Two path cards Two choices, equal weight: a) Provide Campaign Details (structured) · b) Help me define campaign (conversational). ✚ Path b is an in-thread elicitation: the agent asks for the same fields, ≤1 question per turn, and shows progress chips — Product ✓ · Campaign … · Brand ✗ — as an intake_progress artifact. It writes the identical CampaignContext schema; it is elicitation UX, not a second data model. The user may switch to path a at any time and half-filled cards persist.
2 · Three detail cards Three cards sit between the nav and the prompt modal; each opens a modal popup. Card states: empty · partial · ✓ saved. See 2.1. ✚ Popup UX basics: field-level validation, save-per-card (card shows ✓), Esc closes with the draft kept, upload previews, required/optional flags. ✚ Compliance without a new form field — see 2.2.
3 · Rumination → options All three cards ✓ → the thread shows labeled agent steps: retrieving evidence → drafting options → council review. Never a bare spinner. Output: 2–3 campaign_option cards — name-line, description, short storyline, objective echo, why-it-fits. Actions per card: Approve · Regenerate. Free-text refinement from the prompt modal targets the options. No fill needed — inherits Addendum-01 §04 (labeled loading, honest empties, error cards) and the v1 evidence rules: why-it-fits cites retrieved source_ids or says "no evidence in DB". R1–R7 anti-generic rules apply to storylines.
4 · Templates (optional) After approval: a template_picker of curated thumbnails (image or video style references), plus one Skip. Sources: static samples from samples/templates/manifest.json (id, thumb, type, style descriptors) — owner supplies the files. Empty-manifest state is a first-class state, not an error (§03 disabled states). ✚ Semantics: a selected template is a style/composition reference injected into downstream image/video prompts — it constrains look, never copy. Skip = no style constraint at all (style_ref stays null).
5 · Campaign detail The planner produces the campaign detail; it opens in the right panel's Context tab: detailed script (video) or image prompt set (statics), plus shot/slide structure, copy, CTA, claims used. In-thread the agent asks one question: "Generate creative?" ✚ The detail is an artifact (campaign_detail), so panel deep-link, one-panel-at-a-time and the prompt-bar context chip all inherit Addendum-01 §02 unchanged.
6 · Refine loop The user prompts changes to the script/prompt set from the modal. The agent edits only what was named, shows the diff, and the Context tab updates in place with a version marker (v1 → v2, change note in changes[]). No fill needed — this is the v1 diff-only refine rule applied to CampaignDetail.
7 · Generate Creative A model_confirm card posts before anything renders: recommended image/video model, one-line reason, cost, and the note that Settings will later allow overrides (disabled now). The same card asks "One creative, or variants?" See 2.3. No fill needed — cost-before-generate, draft-first offer on video, and per-asset re-roll are existing invariants (Addendum-02 rules 8–9) and are not weakened here.
8 · Creative tab Generated images/videos land in the right panel's Creative sub-tab as a grid: per-item status, preview, download, re-roll, "use as reference". The accepted set plus copy assembles the Ad Card — per-placement copy, ratios, naming string, export bundle — which lands in the thread and in My Campaigns. No fill needed — Ad Card is the v1 deliverable spec re-pointed at campaigns; assembly waits for per-asset acceptance (Addendum-02 rule 10).

2.1 The three cards (path a)

CardFields
Enter Product DetailsName · description · images. 3–8 images — these become the product pack, i.e. the consistency lock carried verbatim into every downstream prompt.
Enter Campaign DetailsObjective (awareness / traffic / conversions — drives the CCF weights) · target audience · platform(s) · optional description · creative type wanted (video or image).
Enter Brand DetailsBrand URL · colour palette selection · font · logo · Fetch from URL · Brand Policy Document (optional upload). Fetch runs the system extractor pipeline — palette, font, logo, tagline — and the user confirms or edits the result. Extraction is a system pipeline, never an agent tool.

2.2 ✚ Compliance without a new form field

Approved claims and banned words are extracted from the Brand Policy Document and the product description, then shown to the user for one-tap confirmation inside the Brand card. The agent produces candidates only; it never sets claims_confirmed itself. The confirmed list is the claims source of truth, and the kill-flag lens is unchanged: a persuasion claim that maps to nothing on that list is a kill flag, not a warning.

2.3 Model confirm, single vs variants

  • Single (default) generates one creative.
  • Variants → the orchestrator proposes 2–3, each with a named delta (different hook / visual treatment / copy angle — never rewordings), a per-variant cost, and a test hypothesis ("B tests hook vs A"). The user picks the count.
  • Variant sets share a variant_group_id on their Ad Cards, so the set is legible later in My Campaigns and in performance memory.
  • The question always precedes generation. No variant set is ever generated without an explicit count choice, and no generation runs without a visible cost plus an explicit UserEvent.
03 · Theme, panel, prompt modal

Dark surface, two tabs, one persistent prompt bar

The --ms-* set is added to the existing token system and scoped to Marketing Studio surfaces. The typography system is unchanged. Contrast is ≥4.5:1 everywhere.

The same applies to danger. Derived text/border values are implementation detail of the token file — the eleven tokens above are the contract.

04 · Agent chain

intake → planner → evaluator → creative orchestrator

IntakeParser with eyes; no advice. Normalizes path a/b into CampaignContext; runs the extraction-confirm loops (brand fetch, claims).
→
PlannerCampaign options (step 3), then the campaign detail (step 5). Evidence rules, R1–R7, diff-only refines: unchanged.
→
EvaluatorAgent Council: three blind seats + a chair. Consolidates into the single, unchanged Feedback schema. One refine loop.
→
OrchestratorEverything after step 5: model confirm, single/variants, generation, seam QA, Creative tab, Ad Card, status lifecycle.

4.1 The Agent Council (this is the change)

v1's single feedback agent becomes a council, following the owner's Agent Council reference (intake → analyst draft → reviewer agents including custom stakeholder reviewers → revised final). The Feedback schema itself does not change.

SeatLenses · what it holds
Performance MarketerHook, offer, angle-fatigue. Owns the saturation lens, including the insufficient-data rule below the niche asset threshold.
Brand GuardianTone, claims versus the confirmed approved list, banned words, visual consistency with palette/logo/tagline. Holds the kill flag.
Platform SpecialistPlacement, format, ad policy.
ChairConsolidates the seats into the single Feedback schema: final rating authority, mandatory lens coverage, ccs_final, fixes, kill flags. Where seats disagree it judges and names the seat; it never averages blindly and never drops a kill recommendation silently.
  • Blind by construction. Each seat scores without the planner's ratings and without sight of the other seats, grounded only in its own RAG slice.
  • One refine loop. Unchanged from v1 — the council does not iterate to consensus.
  • Seats are editable prompt files (prompts/council/seat_*.md, prompts/council/chair.md), mirroring the reference app's editable agent prompts. Optional user-added stakeholder seats ("My CMO") come later; three seats ship as the default bench.
  • All v1 mechanics intact: mandatory lens coverage, the CCS recomputation on the server (the chair's ccs_final is advisory), two-layer citation validation, the platform hard filter and cross-platform downgrade to PRINCIPLE.

4.2 Creative orchestrator

Owns everything after step 5: script/prompt maintenance, model recommendation and the confirm card, the single-vs-variants question, generation jobs, seam QA, Creative-tab population, Ad Card assembly including variant_group_id, and the status lifecycle in My Campaigns. It inherits the Addendum-02 creative-director rules verbatim — editable prompts used as written and never "improved", per-asset acceptance, no generation without a visible cost and an explicit event, post-delivery edits reopen the card and are logged — and adds only the model-confirm card, the variants discipline, and Ad Card assembly. It never generates a variant set unasked.

05 · Schemas

The campaign contract

Paths a and b write the same CampaignContext. Everything downstream keys off it.

// ---- context: one schema, two intake paths ----
CampaignContext {
  name                                  // required, unique per workspace
  product  : ProductBlock  | null
  campaign : CampaignBlock | null
  brand    : BrandBlock    | null
  .complete = product && campaign && brand && brand.claims_confirmed
}
ProductBlock  { name, description, image_upload_ids[]      // 3-8 = product pack }
CampaignBlock { objective: awareness|traffic|conversions,  // drives CCF weights
                target_audience, platforms[], description?,
                creative_type: video|image }
BrandBlock    { url?, palette[], font?, logo_upload_id?, tagline?,
                policy_upload_id?,
                approved_claims[], banned_words[],         // extracted candidates
                claims_confirmed: bool }                   // user one-tap ONLY

// ---- step 3: options ----
CampaignOption  { option_id, name_line, description, storyline,
                  objective_echo, why_it_fits,
                  evidence[] }          // source_ids or honest "no evidence in DB"
CampaignOptions { options[2..3] }

// ---- step 4: templates (style only, never copy) ----
TemplateRef { id, type: image|video, style_descriptors[] }
// Skip => style_ref stays null => no style constraint injected anywhere.

// ---- step 5/6: the detail, versioned in place ----
DetailShot     { slot, duration_s?, visual_prompt, vo_or_copy? }
CampaignDetail { creative_type, shots[1..], copy_primary, cta,
                 claims_used[],        // MUST be a subset of confirmed claims
                 style_ref: TemplateRef|null,
                 version, changes[] }  // refine-loop diff log

// ---- step 7: always before generation ----
VariantSpec  { variant_id, delta, hypothesis, cost_usd }   // delta is NAMED, never a reword
ModelConfirm { recommended_model, reason, cost_usd,
               settings_note = "Model selection coming — using recommended models",
               variants_proposed[] }

// ---- step 8: the deliverable ----
AdCard { id, campaign_id, thread_id, option_id,
         variant_group_id?, variant_id?,          // a variant set shares the group id
         creative_type,
         placements { platform: copy },
         ratios[1..],                             // spec table: 9:16 1:1 16:9 4:5
         naming,                                  // brand_campaign_option_variant_ratio
         media[], total_cost_credits,
         status: draft|ready|live, created_at }

// ---- evaluator ----
SeatReview { seat: performance|brand|platform,
             element_scores[1..], kill_recommendation?, fixes[] }
// The chair consolidates SeatReview[] into the UNCHANGED Feedback schema.

Envelope additions — seven new artifact types

The AgentMessage / UserEvent envelope of Addendum-01 §05 is unchanged. Only the ArtifactType union grows.

// ArtifactType += these seven. Payload keys are the render contract.
intake_progress : { filled:{product,campaign,brand}, next_field|null }
                  actions: —                                // display only
campaign_option : { option: CampaignOption }
                  actions: approve · regenerate
template_picker : { templates:[TemplateRef+thumb], skip_allowed:true }
                  actions: pick_<id> · skip
campaign_detail : { detail: CampaignDetail }
                  actions: generate_creative
model_confirm   : { confirm: ModelConfirm }
                  actions: generate_single · generate_variants_2 · generate_variants_3
creative_set    : { items:[{asset_id, slot, kind, preview_url,
                            status, cost, variant_id?}] }
                  actions: accept_all · reroll_<slot> · use_as_reference_<slot>
ad_card         : { card: AdCard }
                  actions: mark_live

creative_set is an envelope payload shape, not a stored object — the items are asset rows, and the Ad Card is what persists.

06 · My Campaigns

Main tab 2 — lifecycle, spend, and the results loop

Column / controlSpec
Name · objectiveThe campaign name from step 0 and the objective from the campaign block.
StatusLifecycle: Draft → Planned → In production → Ready → Live. Campaign-level. Distinct from the per-card AdCard.status (draft / ready / live), which tracks one deliverable.
Creative countAd Cards produced for this campaign.
Spend to dateCredits, summed from the asset costs across the campaign's threads. Every generation is already logged with its params and cost; this is that log, totalled.
