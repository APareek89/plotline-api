01 · Content Studio — the transformation

Context blocks in, then everything is a conversation

LandContext blocks (v1 §3.1 spec unchanged: guided blocks, required/optional flags, uploads, series name). The only form surface in the product.
→
MorphOn submit, the form collapses into a pinned, editable Context Summary card at the top of a new thread. Viewport becomes an agentic chat with the bottom prompt modal.
→
ThreadAgent drives: inspiration set → format options → concepts in batches → feedback verdicts → options → plan. All approvals in-thread (tap or type).
→
DetailClicking any artifact card opens the right detail panel (§02). Prompt bar stays live; "this" targets the open artifact.
→
DoneFinal plan approved in-thread → series lands in Plans; thread stays as the series' planning record.
  • No stage sidebar anywhere. Stages are the agent's internal sequence (matching Creative Studio's rule from v1). Left panel = series/threads only (§03).
  • In-thread artifact types: context_summary · inspiration_set (cards with description + why-it-works; sample-data/disabled state per v1 rules) · format_options (§07.1) · concept · options · plan · escalation. Each renders as a card stack inside an agent message, never as prose.
  • Approvals are dual-path: every card carries action buttons (Approve / Feedback / Regenerate), and typed commands ("approve c3", "regenerate the second one, punchier") resolve to the same events. Neither path is second-class.
  • Concepts arrive in batches of 3–4 per message with a one-line frame — never all ten at once, never one at a time.
  • Editing the Context Summary after planning starts prompts a confirm: "changes context — re-run plan? (concepts already approved are kept unless affected)".

03 · Left panel & thread naming

Series only, numbered threads

  • Contents: series/project names only — no stages, no settings. Grouped: Active · Done. "+ New series" routes to context blocks; "DIY thread" (Creative Studio) stays in that tab's rail per v1.
  • Numbering: threads of one series are ordinal: AI Content — 01, — 02… Zero-padded 2 digits, assigned at thread creation, never reused or renumbered on delete. The Content Studio planning thread is — 01 by convention; per-post Creative Studio threads continue the sequence.
  • Names come from the required series-name field (v1 rule). Rename allowed from the rail (kebab menu) — renames propagate to Plans; numbers don't change.
  • States: active thread = red left-bar + dot; unread agent activity = dot on the series row; truncate long names with tooltip; search field appears at >8 series.
04 · UX fundamentals

The basics, specified — not assumed

AreaRule
LoadingAgent work shows labeled steps, not a spinner: "retrieving evidence → drafting concepts → feedback pass → validating". Text streams; artifact cards appear as skeletons that fill. Long media jobs (Phase 2) show per-shot progress bars.
Honest empties"No evidence in DB", "sample data — pipeline pending", "insufficient data for saturation" render as designed states (muted, dashed), never as silent gaps or fake confidence. The honesty rules of v1 are UI states, not footnotes.
ErrorsValidation failure after retries → in-thread error card: what failed, one Retry action, never a stack trace. Network loss → thread persists locally, prompt bar disables with a reconnect note.
Destructive confirmRegenerate (overwrites a concept), context edits mid-plan, and thread delete get a confirm; approvals don't.
KeyboardCmd/Ctrl+Enter send · Esc closes panel · / focuses prompt bar · ↑ edits last user message.
AccessibilityPanel is an aria-labeled complementary region with focus trap while overlaying; all actions reachable by tab; card actions have text labels (icons never alone); contrast ≥ 4.5:1 on both light thread and dark studio surfaces; prefers-reduced-motion kills the morph animation and streaming shimmer.
MotionOne signature transition only: context form → summary card collapse (≤300ms). Panel slides ≤200ms. Nothing else animates.
PersistenceThreads restore scroll position, open panel, and unsent prompt-bar draft per thread.
05 · Interaction contract (adds to §3.9)

The envelope every agent message travels in

This is the one thing Claude Code must implement first — the UI renders cards from it, approvals flow back through it, and the prompt deltas below depend on it.

// AgentMessage — every agent turn, all studios
AgentMessage {
  thread_id
  text: string(≤2 short sentences)      // conversational envelope only
  artifacts [{
    type: "context_summary"|"inspiration_set"|"format_options"|"concept"|
          "plan"|"options"|"escalation"|"confidence_card"|"script_package"|
          "brand_kit"|"final_delivery"
    id, title,
    payload: <the §3.9 schema for that type — unchanged>
    actions [{ id, label, style:"primary"|"secondary"|"danger", event }]
  }]
  question: string | null                // at most ONE
}
// UserEvent — both input paths normalize to this
UserEvent {
  thread_id
  type: "text" | "action"
  text?: string                          // free typing
  action?: { artifact_id, event }        // button tap
  panel_focus?: artifact_id              // set while a detail panel is open
}
// Server-side: typed approvals ("approve c3") are parsed to action
// events; both paths hit the same handler. Validators unchanged (§3.9).
06 · Prompt deltas (§11)

Exact text to append — nothing else in §11 changes

Append to Shared agent policy

CONVERSATIONAL PROTOCOL
8. You speak inside a thread. Every reply is an AgentMessage envelope:
   text ≤2 short sentences, artifacts[] as structured payloads, at most
   ONE question. The UI renders artifacts as cards — never restate an
   artifact's content in text, never present a plan as prose.
9. Reference artifacts by id ("concept c3"), not by re-describing them.
10. Deliver concepts in batches of 3–4 artifacts per message, each batch
   framed in one line.
11. If the incoming UserEvent carries panel_focus, resolve "this/it" to
   that artifact.
12. Action events and typed approvals are the same signal. Never ask the
   user to confirm what an action event already confirmed.

Append to Planner agent

DELIVERY (thread mode)
- PASS 0.5 (new, before PASS 1): propose 2–3 series FORMATS as
  format_options — {format_id, name, vehicle, why_fits (evidence rules
  apply), effort, cadence_fit}. Draw from the format-library corpus and
  inspiration retrieval. Wait for the user's pick/edit; PASS 1 concepts
  are episodes of chosen formats.
- Emit concepts as artifact batches per the protocol. On refine, emit
  only changed concepts (diff rule unchanged) with a one-line summary
  of what changed and why, citing the feedback verdict ids.

Append to Feedback agent

- Your element_verdicts and lenses are rendered verbatim in the
  artifact's Activity tab — write reasons for the creator's eyes:
  concrete, one sentence each, no meta-commentary about being an AI.
- New lens inputs (§07): saturation returns "insufficient_data" below
  the niche asset threshold; cross-platform evidence must be flagged
  and downgraded to PRINCIPLE; apply the anti-generic rules R1–R7.

Creative director + brand-kit prompts: unchanged except rule 8–12 inheritance via shared policy.

07 · Committed batch (previously parked)

Format stage, anti-generic rules, red-team fixes

7.1 Format stage + intake fields

  • PASS 0.5 as specced in §06: planner proposes 2–3 repeatable formats before any concepts; user picks in-thread. Concepts become episodes; Plans shows format per series.
  • Format library = new KB corpus dimension: entries like prompt-based utility, MCP/tool demo, skill showcase, role-rotation demo, myth-bust, challenge — each with audience-fit notes and feasibility requirements. Seeded manually (~15 entries), enriched by the curator later.
  • Three new context fields (§3.1): audience sophistication (novice / practitioner / expert) · tool access ("what can you actually demo") · positioning depth (beginner-guide vs power-user). All required — R1 and format feasibility depend on them.

7.2 Anti-generic rules R1–R7

#RuleTestEnforced by
R1Audience-knowledge floorConcept states "assumed known" vs "the new thing"; new-thing inside the audience's known set → rejectFeedback lens
R2Receipt requiredAdvice payloads name a demonstrable artifact in creative_directionValidator (field) + lens (is it proof)
R3Specificity floorHook contains ≥1 of {role, number, artifact, outcome}; banned-abstraction lexicon ("game-changer", "boost productivity"…)Validator (lexicon) + lens
R4Angle saturation, not topicFeedback articulates the packaging delta vs nearest neighbors in one sentence; can't → downgradeFeedback lens
R5Minus-hook testStrip the hook; remainder reads as documentation → kill flagFeedback lens
R6FreshnessTool/trend references need a trend-corpus citation with as_of ≤ 45dValidator (date) — active once trends corpus ships
R7Effort–value symmetryL-effort + generic payload → rejectFeedback lens

Placement: mechanical checks live in the server-side validator (prompts drift, validators don't); judgment checks are feedback-agent lenses; the planner prompt carries them only as generation guidance. Rule telemetry logged per concept for monthly tuning.

7.3 Red-team fixes (from the Phase-1 simulation)

FixSpec

7.4 Differentiation rubric — utility niches

For utility content (prompts, tools, how-to): Differentiation = distinctive packaging + receipts on a possibly saturated topic, not novel information. Topic repetition is acceptable; angle-and-package sameness is the failure. Rubric text updates inside the element definition; weights unchanged.
